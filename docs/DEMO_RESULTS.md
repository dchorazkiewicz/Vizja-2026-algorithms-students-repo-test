# Demonstration results

List 01 is tested against three simulated student submissions. The purpose is to prove that the grader can distinguish **correct output** from **algorithmic method**.

## Representative result

| Profile | Functional checks | Methodological findings | Interpretation |
|---|---:|---:|---|
| Strong | 23 / 23 | 0 | Correct results and intended algorithmic method |
| Functionally correct but inefficient | 23 / 23 | 7 | Correct outputs, but several method and efficiency issues are observable |
| Weak | 9 / 23 | 7 | Both correctness and algorithmic problems are present |

## First occurrence

For target 3 in [8, 3, 5, 3, 9, 10], the strong implementation returns 1 after reading only indices [0, 1].

The functionally correct but inefficient implementation also returns 1, but reads all six elements. An output-only test sees no difference; runtime instrumentation does.

## Minimum and maximum

For 100 elements, the strong implementation performs approximately one pass: 101 element reads and 198 comparisons.

The functionally correct but inefficient implementation performs 200 reads and two sequence iterations. Both are linear, but the second performs unnecessary work.

## Hidden quadratic behaviour

The weak running-sum implementation repeatedly evaluates prefixes using sum(values[:i + 1]). Its functional checks for that task pass, but AST detects both sum and slicing.

Measured element reads:

~~~text
n = 64   →   2,080
n = 128  →   8,256
n = 256  →  32,896
n = 512  → 131,328
~~~

Observed doubling exponents are approximately 1.989, 1.994 and 1.997, providing strong empirical evidence of quadratic growth.

## Why this matters

The feedback model is not limited to "your answer is wrong".

It can also say: "your answer is correct, but the implementation scans unnecessary data, allocates an avoidable copy, misses early termination, or exhibits a worse growth pattern than required."
